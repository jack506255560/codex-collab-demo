# Codex Collab Demo

[简体中文](README.md) | [日本語](README.ja.md) | Русский

Небольшой демонстрационный репозиторий для проверки полного цикла совместной работы агентов: от изменения файлов и запуска тестов до передачи результата и проверки. Он отделён от рабочих проектов и содержит простой пример на `sh`.

## Быстрый старт

Нужен POSIX-совместимый интерпретатор `sh`. Дополнительные пакеты для запуска примера и базовых тестов не требуются. Выполняйте команды из корня репозитория:

```sh
sh greet.sh
# hello, world

sh greet.sh Alice
# hello, Alice

sh test.sh
# base checks passed
```

Комментарии под командами показывают ожидаемый вывод. Тест завершится с ненулевым кодом, если одна из двух базовых проверок не пройдёт.

## Как работает пример

[`greet.sh`](greet.sh) использует только первый аргумент как имя и печатает `hello, имя` с переводом строки. При отсутствии аргумента или пустой строке имя по умолчанию — `world`. Остальные аргументы игнорируются; флаги скрипт не разбирает.

| Команда | Ожидаемый вывод | Что показывает пример |
| --- | --- | --- |
| `sh greet.sh ''` | `hello, world` | Пустое имя заменяется на `world` |
| `sh greet.sh 'Ada Lovelace'` | `hello, Ada Lovelace` | Кавычки сохраняют имя с пробелом в одном аргументе |
| `sh greet.sh Alice Bob` | `hello, Alice` | Используется только первый аргумент |
| `sh greet.sh --upper` | `hello, --upper` | `--upper` воспринимается как имя |

[`test.sh`](test.sh) проверяет только запуск без аргументов и запуск с именем `Alice`. Случаи из таблицы поясняют поведение скрипта и не входят в этот базовый тест.

### Зачем нужна задача T-001

Демонстрационная задача `T-001` предлагает добавить в `greet.sh` режим `--upper`. В текущем примере он **намеренно не реализован**: вывод остаётся `hello, --upper`. Это исходное состояние для упражнения, а не ошибка установки.

Записи о задаче служат тестовыми данными для Git-протокола. Их наличие не подтверждает автоматическое назначение, выполнение или одобрение задачи. Запуск локальных скриптов также не подтверждает развёртывание приложения Feishu, межмашинного сервиса или Runner. Фактическое состояние сервисов и задач проверяйте отдельно через инструменты совместной работы.

## Где находятся файлы и данные

| Файл или ветка | Назначение |
| --- | --- |
| [`greet.sh`](greet.sh), [`test.sh`](test.sh) | Локальный пример и две базовые проверки |
| [`AGENTS.md`](AGENTS.md), [инструкция `team-collab`](.agents/skills/team-collab/SKILL.md) | Правила работы над общей задачей |
| `main` | Пример, тесты и документация проекта |
| `agent-collab` | Отдельная ветка с задачами и событиями |
| Назначенная ветка задачи | Изменения кода или документации для проверки |

**Не сливайте `agent-collab` в `main`.** Данные задач и изменения проекта проходят разными путями.

## Порядок совместной работы

1. Прочитайте [`AGENTS.md`](AGENTS.md) и [инструкцию `team-collab`](.agents/skills/team-collab/SKILL.md). Через инструменты совместной работы получите спецификацию задачи, последнюю передачу результата и замечания проверки, если они есть.
2. Работайте в выделенном рабочем дереве Git и назначенной ветке, начиная с указанного исходного коммита. Выполняйте только текущий этап; не используйте незакоммиченные изменения другого участника.
3. Запустите `sh test.sh` и проверки, связанные с изменениями. Для документации проверьте примеры команд и локальные ссылки. Просмотрите разницу версий, добавьте в индекс только нужные файлы и создайте коммит.
4. Через инструменты совместной работы передайте краткое описание изменений, результаты проверок и ссылку на коммит. Передайте результат следующему участнику либо запросите проверку согласно текущему этапу. Если требуется одобрение человека, дождитесь его: готовность коммита ещё не означает одобрения или завершения задачи.

Не сохраняйте в Git секреты, учётные данные, приватные локальные пути или полные переписки.
